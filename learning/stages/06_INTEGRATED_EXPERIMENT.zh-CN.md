# 阶段六：综合实验与独立分析

[返回总路线](../QEMU_LEARNING_DESIGN.zh-CN.md) · [上一阶段](05_DEVICES_AND_INTERRUPTS.zh-CN.md) · [下一阶段：异常与中断](07_TRAPS_INTERRUPTS_AND_TIMERS.zh-CN.md)

## 1. 最终目标

**实验目标：** 复现求和与串口输出基线及两个对照变体，用 Guest 状态、Host 调用栈和翻译日志形成可复现实验报告，并定位一次设备状态变化导致的输出差异。

建议 5 次学习，每次 1～2 小时。将前五阶段证据组织成一份可以复现的报告，解释：**Guest 执行求和指令，把结果写入 RAM，随后通过 MMIO 输出字符。**

本阶段不以新增复杂代码为目标。先复现基线，再做小变化，最后报告结论和局限。所有实验延用个人本地研究范围。

## 2. 第一次学习：冻结输入

在仓库根目录记录：

```bash
git rev-parse HEAD
./build-study/qemu-system-riscv64 --version
riscv64-linux-gnu-gcc --version
sha256sum build-study/study-lab/program.S build-study/study-lab/program.ld build-study/study-lab/program.elf
```

另存完整构建命令、QEMU 启动命令和使用的 GDB 版本。若源码有本地修改，记录相应 diff；只记录 HEAD 不足以描述带修改的构建。

建议在 `build-study/study-lab/report/` 保存报告和证据，按 `baseline`、`variant`、`host-debug`、`guest-debug` 区分实验轮次。运行产物不需要混入学习文档目录。

## 3. 第二次学习：完成基线验证

使用第一阶段 ELF，不附加 GDB，输出到独立文件。确认得到一个 `K`，结束进程。然后单独一轮 Guest 调试，验证 result 为 15。

记录下面的证据链：

| 问题 | 证据 | 来自哪一侧 |
| --- | --- | --- |
| 从哪里开始执行？ | ELF 入口与初始 PC | Guest / 文件元数据 |
| 做了哪几次加法？ | 循环寄存器记录 | Guest GDB |
| 指令如何翻译？ | 解码入口、翻译函数和 TCG 日志 | QEMU / Host |
| 结果存在哪里？ | result 地址及四个字节 | Guest 内存观察 |
| 哪次访问输出字符？ | uart_write 指令与寄存器值 | Guest GDB |
| 设备如何处理？ | serial_mm_write 到后端的调用栈 | Host GDB |

这些证据可来自不同轮次，但每轮必须使用相同输入和配置；不能假装它们是同一次精确时间跟踪。基线字符固定为 K，并未编码求和值，所以两项结果必须分别验证。

## 4. 第三次学习：两个有预期的变体

### 变体 A：改变运算，保留输出

复制基线汇编，将循环上界从 6 改为 4，编译为独立 ELF。预期 `result=6`，字符仍为 `K`。解释为什么算术结果改变不必改变设备访问路径。

### 变体 B：改变字符，保留运算

从基线复制另一份，将字符 75 改为 65。预期 `result=15`，字符为 `A`。在设备回调处核对 value 从 75 变成 65。

每个变体使用独立文件名和匹配的调试符号。对比实际结果与预期，差异出现时从最早不一致的观察点定位。

| 实验 | result | UART 字节 |
| --- | --- | --- |
| baseline | 15 | `0x4b` |
| variant A | 6 | `0x4b` |
| variant B | 15 | `0x41` |

## 5. 第四次学习：练习定位问题

选择一种低风险变更进行排查，并在完成后恢复基线：

- 故意用旧 ELF 启动：比较文件校验值、反汇编和实际寄存器，识别构建产物不一致。
- 把串口后端改为文件：解释终端没有字符的原因，并核对文件输出。
- 加 `-S` 但不连接 GDB：说明为什么没有执行输出，而不是断言 CPU 卡死。

增加一个设备状态挑战：在独立副本中将初始 LCR 从 3 改成 0x83（置 DLAB），其余保持基线，先预测 UART 偏移 0 的含义，再用宿主断点确认写入的是分频器字段还是发送寄存器。设置有界观察时间，保存无预期字符时的调用证据，随后恢复 LCR=3 重跑。该挑战验收“状态改变访问语义”，不只比较字符常量。

不要通过随机非法访存制造问题；基线没有异常处理器，无法提供清晰异常报告。

排查顺序建议：输入文件与参数→Guest PC→目标指令执行→RAM 结果→MMIO 参数→设备状态→后端输出。每次只改一个条件，避免多个变化互相掩盖。

## 6. 第五次学习：写报告与自我讲解

报告使用以下模板，填写实际数据，不只复制标题：

```text
1. 问题与范围
   我要验证什么？哪些行为不在本实验范围？
2. 环境与输入
   QEMU 提交/本地修改、工具版本、ELF 校验值、启动命令。
3. 预期行为
   result、UART 字节、关键断点位置。
4. 执行证据
   Guest 状态、Host 调用栈、TCG 日志、设备回调参数。
5. 路径解释
   指令→翻译/执行→RAM→MMIO→字符后端。
6. 对照实验
   变体改变了什么，结果为何符合或不符合预期？
7. 限制和待办
   尚未验证的分页、中断、时序和一致性问题。
8. 复现步骤
   从已有源码与工具开始，别人如何重做？
```

用五分钟口述整个路径。别人问“你怎么知道”时，应能指出一项对应证据，而不是只说“源码就是这样”。

## 7. 最终完成标准

- [ ] 从保存的命令重新构建并运行基线。
- [ ] 两个变体得到表中预期结果。
- [ ] 每个关键结论能定位到源码、日志或调试观察。
- [ ] 明确区分翻译发生与指令执行、Guest 地址与 Host 地址。
- [ ] 承认本实验没有验证真实 CPU 周期、cache/NoC 竞争和分页行为。
- [ ] 中断动态验证若未完成，单独列为后续任务。
