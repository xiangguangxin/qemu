# QEMU 学习路线设计文档

## 1. 文档定位

本文设计一套以源码阅读、调试和本地实验为核心的 QEMU 学习方案。学习主线为：

**运行系统 → 调试启动 → 跟踪指令 → 理解访存 → 跟踪设备 → 综合验证。**

适用对象：具备基本 C 语言和 Linux 使用经验，希望理解 QEMU 工作原理的学习者。

源码基线：当前仓库 `VERSION` 为 `11.1.50`。函数和目录以当前仓库为准；后续版本发生调整时，应通过符号搜索重新定位。

使用范围：个人学习、源码分析、调试和本地实验。依据仓库 [代码来源政策](../docs/devel/code-provenance.rst)，本文及相关 AI 生成内容不得包含在提交给 QEMU 上游的贡献中。

本文作为总入口，六个阶段的具体教材放在 `learning/stages/`。先完成每阶段的必做实验，再根据需要选择 Linux、分页或中断进阶任务。所有实验命令默认从仓库根目录执行，进入构建目录的步骤会明确说明。

### 1.2 六阶段共用的实验主线

第一阶段提供完整的 RISC-V 汇编和链接脚本，生成 `program.elf`：

```text
从 0x80000000 启动
  → 求 1 + 2 + 3 + 4 + 5
  → 将 15 写入 RAM 中的 result
  → 向 UART 写字符 K
  → 停在 done 循环
```

第二阶段验证状态，第三阶段解释指令执行，第四阶段比较 RAM 与 MMIO，第五阶段跟通设备，第六阶段用变体证明理解。字符 K 是固定输出，并不代表计算结果正确，所以求和值和字符必须分别检查。

采用裸机主线是为了减少镜像、固件和根文件系统对进度的影响。Linux 启动到 shell 保留为阶段一扩展；分页和 Guest 中断处理需要额外环境，不作为裸机实验已经验证的内容。

## 2. 学习目标与范围

完成学习后，应能够：

1. 独立构建 QEMU，并运行一个指定架构的 Guest。
2. 解释启动参数如何影响 CPU、内存、开发板和设备配置。
3. 分别调试 QEMU 进程和 Guest 程序。
4. 描述 Guest 指令经 TCG 翻译并执行的主要过程。
5. 区分 Guest 虚拟地址、Guest 物理地址和 Host 地址。
6. 跟踪一次 RAM 访问和一次 MMIO 设备访问。
7. 通过日志、断点和调用栈验证源码阅读结论。

首轮以 **RISC-V 64 位、virt 开发板、TCG、单个 vCPU** 为实验配置。选择这一配置是为了集中学习 CPU、内存和设备之间的关系。如果已有 ARM 或 x86 项目，可替换目标架构，并保留阶段顺序。

首轮暂缓深入：多线程 TCG、动态迁移、复杂 PCI 拓扑、VFIO、存储和网络性能优化。KVM 在后续虚拟化分支中学习。

## 4. 总体知识地图

### 4.1 核心概念

| 概念 | 需要回答的问题 |
| --- | --- |
| Host / Guest | 哪些代码运行在宿主进程中，哪些属于被模拟的系统？ |
| 用户态 / 系统模拟 | 是运行一个程序，还是提供 CPU、内存和设备组成的机器？ |
| TCG / KVM | 执行依赖动态翻译，还是宿主内核与硬件虚拟化？ |
| CPU / Machine / Device | 处理器状态、整机配置、外设行为分别由谁负责？ |
| RAM / MMIO | 地址访问对应内存存储，还是设备寄存器操作？ |

### 阶段一：建立概念并构建运行环境

**时间：第 1 周，前 2～3 天梳理概念。**

详细教材：[阶段一：构建环境与第一次运行](stages/01_ENVIRONMENT_AND_FIRST_RUN.zh-CN.md)。包含可保存的汇编与链接脚本、构建命令、启动命令和 Linux 扩展模板。

任务：

1. 理解第 4 节的核心概念，浏览源码地图。
2. 只构建 `riscv64-softmmu`，减少构建范围。
3. 查看支持的机器和 CPU 类型。
4. 编译教材中的裸机程序，运行到串口输出 K；Linux 登录界面作为扩展目标。
5. 保存启动命令并解释参数作用。

依赖准备完成后，在仓库根目录执行：

```bash
mkdir -p build-study
cd build-study
../configure --target-list=riscv64-softmmu --enable-debug
ninja
./qemu-system-riscv64 --version
./qemu-system-riscv64 -machine help
./qemu-system-riscv64 -cpu help
```

这是构建示例，未在编写本文时实际执行。裸机完整启动命令见阶段教材；Linux 启动命令需要匹配所选择的固件、内核和根文件系统。

重点参数：`-machine`、`-cpu`、`-m`、`-smp`、`-accel tcg`、`-bios`、`-kernel`、`-append`、`-drive`、`-device`、`-nographic`。

产出与验收：

- 一份环境记录和可重复执行的启动命令。
- 一份裸机串口输出记录及 ELF 入口检查结果。
- 能说明 CPU 数量、RAM 大小和启动镜像分别如何指定。

### 阶段二：跟踪整机启动

**时间：第 2 周。**

详细教材：[阶段二：跟踪启动并掌握两侧调试](stages/02_BOOT_AND_DEBUG.zh-CN.md)。分别给出宿主 GDB 启动、Guest 连接、断点及预期数值。

先建立两种调试方式的区别：

| 调试对象 | 方式 | 观察内容 |
| --- | --- | --- |
| QEMU 进程 | 宿主 GDB 启动或附加 QEMU | C 函数、对象、回调、调用栈 |
| Guest 程序 | Guest GDB 连接 QEMU GDB stub | Guest 指令、寄存器、内存 |

在完整系统启动命令中加入 `-S -s`，可使 Guest 暂停并开启默认 1234 端口的 GDB 服务。随后使用支持 RISC-V 的 GDB 连接 `target remote localhost:1234`。符号文件应与被调试程序匹配。

源码路标：

| 位置 | 观察问题 |
| --- | --- |
| `system/main.c` | 进程如何进入初始化？ |
| `system/vl.c`：`qemu_init()` | 参数如何参与整机初始化？ |
| `hw/riscv/virt.c`：`virt_machine_init()` | CPU、RAM 和设备如何组合？ |
| `target/riscv/cpu.c`：`riscv_cpu_realize()` | CPU 如何完成初始化？ |
| `system/runstate.c`：`qemu_main_loop()` | 系统如何进入运行控制主循环？ |

这些是阅读和断点入口，不代表直接调用顺序。实际路径包含类型注册、对象创建和回调；主循环也不等同于 vCPU 指令执行循环。

产出与验收：

- 一张包含关键回调的启动流程图。
- 两份调用栈：整机初始化、CPU 初始化。
- 修改启动参数中的内存大小，在调试器中确认其生效位置。

### 阶段三：跟踪指令翻译与执行

**时间：第 3～4 周。**

详细教材：[阶段三：跟踪指令翻译与执行](stages/03_TCG_AND_INSTRUCTIONS.zh-CN.md)。按照八次学习追踪 add、addi 和 bne，比较反汇编、IR 与执行证据。

实验程序仅包含少量整数加法、条件分支和循环。先确认程序的运行方式；Linux 用户态 ELF 需要相应用户态环境，不能直接当作裸机系统镜像使用。

研究路径：

```text
Guest 指令字节
    → 解码和架构相关翻译
    → TCG 中间表示
    → Host 机器码
    → 执行并更新 Guest 状态
```

重点阅读：

- `target/riscv/insn32.decode`：指令编码描述。
- `target/riscv/tcg/translate.c` 及相关实现：指令语义如何翻译。
- `target/riscv/tcg/insn_trans/trans_rvi.c.inc`：本实验整数指令的翻译实现。
- `accel/tcg/`：Translation Block（TB，翻译块）的调度与执行。
- `tcg/`：中间表示与代码生成。
- [TCG 概述](../docs/devel/tcg.rst)与 [TCG 操作](../docs/devel/tcg-ops.rst)。

实验步骤：

1. 反汇编小程序，选择一条加法和一条分支指令。
2. 用 Guest GDB 验证寄存器和 PC 变化。
3. 使用 `-d help` 查看本版本日志选项，按需选择指令及翻译日志。
4. 对照源码定位指令翻译过程。
5. 观察循环中的 TB 复用，理解翻译与执行的区别。

产出与验收：能解释加法的输入输出、分支如何影响执行，以及循环为什么通常无需每次重新翻译。记录时区分“翻译过一次”和“执行过一次”；翻译日志不能直接作为动态执行次数。

### 阶段四：跟踪地址转换与访存

**时间：第 5 周。**

详细教材：[阶段四：地址空间、RAM 与 MMIO](stages/04_MEMORY_AND_ADDRESS_SPACES.zh-CN.md)。包括内存字节检查、Monitor 映射查看和 UART 回调参数核对。

分别研究两条概念路径：

```text
Guest load/store → 地址转换与权限检查 → RAM
Guest load/store → 地址转换与权限检查 → MMIO 设备回调
```

实际实现存在 TLB 命中等快速路径，不应假定每次访问都会走完整的慢路径调用链。

重点概念：`MemoryRegion`、`AddressSpace`、Guest 虚拟地址、Guest 物理地址、Host 地址、软件 TLB、访存异常。

阅读入口：

- [内存模型](../docs/devel/memory.rst)。
- [访存接口](../docs/devel/loads-stores.rst)。
- `system/memory.c`。
- `target/riscv/tcg/cpu_helper.c`。

实验：先观察已知 RAM 地址的读写，再观察一个已知 MMIO 地址的访问。记录分页状态与地址类型，避免把 Guest 地址直接作为宿主指针使用。

产出与验收：整理一张地址转换示意图，并说明 RAM 写入与串口寄存器写入分别触发什么行为。

### 阶段五：跟踪串口设备

**时间：第 6～7 周。**

详细教材：[阶段五：串口设备、对象模型与中断路径](stages/05_DEVICES_AND_INTERRUPTS.zh-CN.md)。区分 MMIO 包装、寄存器实现、字符后端及中断控制器。

从 `hw/riscv/virt.c` 的串口创建位置进入设备实现，逐项研究：

1. 类型注册和实例创建。
2. 属性设置与 `realize`。
3. 设备复位。
4. MMIO 映射、访问宽度和寄存器回调。
5. 中断产生与连接。
6. 字符设备后端如何输出到宿主终端。

配套阅读：[QOM](../docs/devel/qom.rst)、[设备 API](../docs/devel/qdev-api.rst)。对象系统按当前调用链需要学习，先掌握类型、实例、类和回调之间的关系。

实验：让 Guest 输出一个确定字符，在宿主 GDB 中停到对应设备写回调，记录访问地址、偏移、宽度和值。串口发送可能采用轮询；中断路径应单独确认，不能由字符输出成功推断已经触发中断。

产出与验收：给出从 Guest 写寄存器到宿主终端出现字符的流程，并标注设备模型和字符后端的分工。

### 阶段六：综合实验

**时间：第 8 周。**

详细教材：[阶段六：综合实验与独立分析](stages/06_INTEGRATED_EXPERIMENT.zh-CN.md)。提供基线与变体的结果表、故障定位练习及报告模板。

实验主题：观察一个小程序的指令执行、RAM 访问和串口输出。

步骤：

1. 固定源码版本、Guest 程序和启动参数。
2. 用 Guest GDB 确认关键指令及寄存器变化。
3. 用 TCG 日志观察相应代码的翻译。
4. 记录一次 RAM 访问结果。
5. 用宿主 GDB 观察一次串口设备回调。
6. 将日志、断点和源码关系整理成实验报告。

最终验收：

- 按记录可以从构建产物重新启动实验。
- 可以清楚区分 Host 与 Guest 两侧的观察结果。
- 每个主要结论至少有源码位置、调用栈或日志之一作为依据。
- 能完整解释“指令执行—内存访问—设备输出”的关联。

## 6. 学习记录与工作方法

每次阅读只围绕一个具体问题，例如“这个地址为什么命中串口设备”。采用以下循环：

**提出问题 → 搜索符号 → 阅读局部源码 → 设置断点 → 观察结果 → 更新结论。**

搜索示例，在仓库根目录执行：

```bash
rg -n 'qemu_init\(' system/
rg -n 'virt_machine_init' hw/riscv/
rg -n 'riscv_cpu_realize' target/riscv/
```

每次实验记录以下内容：

| 字段 | 内容 |
| --- | --- |
| 问题 | 本次准备解释的一个行为 |
| 环境 | 源码提交、构建配置、镜像、工具版本 |
| 操作 | 完整启动命令、调试命令、输入 |
| 预期 | 预计命中的函数或状态变化 |
| 证据 | 断点、调用栈、日志、寄存器或内存值 |
| 结论 | 已确认事实、推测、尚未解决的问题 |

优先使用已有日志、GDB 和 trace 机制。若需要修改代码辅助理解，将其限定为本地实验，并记录改动与观察目的。

### 6.1 每次学习的固定节奏

1. 用 10 分钟回顾上次证据，写下本次唯一的核心问题。
2. 用 20～30 分钟阅读相关文档与局部源码，预测实验结果。
3. 用 30～50 分钟运行、下断点或分析日志。
4. 用 10～20 分钟记录实际观察、修正理解并回答自测题。

连续两次没有进展时缩小问题。例如从“读懂 TCG”改为“找出 add 的源寄存器如何进入翻译函数”，不要仅靠延长浏览源码的时间推进。

### 6.2 每阶段的完成状态

使用三种状态记录：已运行验证、仅源码确认、尚未完成。能解释概念不等于已经通过动态实验；看到日志也不等于已经理解全部路径。

推荐每个阶段保存一页摘要：核心问题、三项已确认事实、一张关系图、关键命令、证据路径、尚未解决的问题。完成一个阶段后，尝试在不看教材的情况下重做最小实验。

### 6.3 常见学习误区

| 误区 | 改进方式 |
| --- | --- |
| 从 main 开始逐行读完整仓库 | 先带着具体行为定位回调和调用栈 |
| 看到串口输出就认为一切正确 | 分别检查计算、内存、设备与 IRQ |
| 用翻译断点次数当指令执行次数 | 区分生成 Host 代码与执行 Host 代码 |
| 把地址直接复制进另一个调试器 | 先确认地址属于 Guest 还是 Host |
| 把源码阅读当成已经实现的能力 | 给每个结论标明验证状态 |
| 一开始就做 SystemC 时间同步 | 先掌握设备代理、地址空间和反向通信基础 |

## 7. 常见阻碍与处理

| 阻碍 | 处理方式 |
| --- | --- |
| 构建依赖缺失 | 依据 configure 报错和本地构建文档补齐依赖 |
| Guest 启动失败 | 分别确认固件输出、内核输出、根文件系统挂载阶段 |
| 宿主断点不命中 | 确认实际运行的是调试构建、后端为 TCG、路径确实被使用 |
| Guest 符号错位 | 确认符号文件、加载地址和程序版本匹配 |
| 阅读被大量宏和回调打断 | 先记录实际调用栈，再补读类型注册和对象关系 |
| 日志量过大 | 缩小程序与观察区间，一次只验证一个行为 |
| 过早深入优化细节 | 回到阶段验收问题，先完成可解释的执行路径 |
